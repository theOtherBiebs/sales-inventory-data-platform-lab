# Architectural decisions (milestone 1)

## ADR-001: Local stdlib vertical slice first
**Decision:** CSV + Python stdlib with generated, entirely synthetic sales and inventory. **Why:** A learner can run tests without cloud credentials, billing, or setup; each layer is inspectable. **Cost:** No distributed scale, ACID transactions, Unity Catalog enforcement, streaming, or production orchestration. Revisit when platform access is available.

## ADR-002: Explicit layer contracts
**Decision:** Bronze copies CSV inputs as-is; silver validates dates, SKU reference membership, positive sales units/prices, nonnegative inventory, and fixed headers. For sales, the highest **valid** positive integer `source_version` per `event_id` wins, independent of CSV order. Identical same-version replays are ignored; different valid payloads tied at any version fail closed instead of silently deciding by file order. Invalid rows (including bad versions) are quarantined; malformed CSV structure/schema fails the build. Inventory date/SKU still uses last-valid-file-row selection. **Why:** Arrival order is not revision order: a late replay of version 1 must not undo version 2. **Cost:** Versions must come from a trusted source with a documented per-event monotonicity contract; invented or reset versions cannot be reconciled here. A conflict fails before new silver/gold writes, but existing outputs from a prior successful build may remain because CSV writes are not atomic—do not consume them without run status. Rejected CSV may expose sensitive data if real inputs were substituted; only synthetic data is authorized. Production needs secure quarantine, schema evolution, PII policy, and reconciliation alerts.

## ADR-003: Metric semantics before infrastructure
**Decision:** Gold date/category grain, event-price sales revenue in cents, end-of-day on-hand stock. **Why:** Prevent grain and floating-point errors; the same number can be tested locally and later implemented in SQL. **Cost:** No returns, taxes, promotions, currency conversion, SKU history, sell-through adjustment, missing inventory snapshot policy, or reconciliation to financial systems. Treat stock zeros as ambiguous unless source completeness is assured.

## ADR-004: Deterministic full rebuild
**Decision:** Build regenerates outputs from landing; `run` first replaces synthetic inputs. **Why:** Simple repeatable baseline. **Cost:** Not atomic, concurrent-safe, scalable, or incremental. Production needs idempotent ingestion IDs, transactional Delta writes, checkpointing, and tested backfills. A late correction for an older business date changes that date/category gold result: the toy full rebuild recomputes all dates, while an incremental system must identify and reprocess the impacted partitions (including both old and new date/category if a correction moves a sale). A watermark that drops older arrivals sacrifices correction completeness; choose a retention/lookback window, exception queue and manual backfill policy deliberately.

## ADR-005: Delta MERGE conceptual mapping (not executed)
A production Silver Delta design would validate/quarantine first, then deduplicate each incoming batch by `event_id` and maximum trusted `source_version`, rejecting contradictory same-version payloads even for older versions. MERGE on `event_id`: update only when source version is greater than the target version; insert when absent; equal identical versions are no-ops, equal conflicting versions are errors. The batch must not expose multiple source rows per target key to MERGE. Keep a replayable Bronze history and record source identity/version in Silver; use transactional writes and recompute affected Gold keys after corrections. This is a conceptual mapping, **not** a working Spark/Delta implementation or cloud execution. Late data outside retention and versions that regress upstream require explicit operator reconciliation.
