# Staged Databricks / Terraform / GitHub CI plan (proposal only)

Nothing in this document provisions resources or publishes a repository. Advance only with an approved cloud account, budget, and access model.

1. **Local gate (now):** Commit source, docs, and tests, not generated data; run `python -B -m unittest discover -s tests -v`. A minimal GitHub Actions workflow (`.github/workflows/test.yml`) runs the standard-library tests on PRs and pushes to `main` with read-only repository permissions. It has not run on GitHub yet; no green badge is claimed. Version matrix, lint/type checks, dependency scan, and branch protection remain future work.
2. **Dev platform design:** With a platform owner, choose a Databricks account/workspace and cloud region, storage and networking pattern, service principals/workload federation, secret management, budget alerts, naming and tagging. Review Terraform provider versions and remote state encryption/locking before authoring modules. Separate dev and prod state; never place tokens or state files in Git. Use reviewed plan/apply boundaries and drift detection; prohibit PR-triggered apply.
3. **Catalog + ingestion:** Terraform could manage dev Unity Catalog catalog/schema, storage credential and external location where appropriate, least-privilege grants, and a service identity. Ingest generated CSV into Bronze Delta with source metadata; write contract tests for duplicates and bad records. Validate whether managed tables/volumes fit governance policy; don't assume external locations are necessary.
4. **Transform + workflow:** Port silver and gold to Spark SQL/PySpark Delta tables with deterministic source versions and MERGE/backfill behavior. Add a Workflows DAG (ingest → validate → aggregate), retries, data-quality thresholds, job ownership, alerts, run logs, and a cost ceiling. Compare 14 gold rows and key metrics against the local fixture, then test rerun/late arrivals.
5. **Delivery:** A future GitHub CI pull request checks tests, formatting, Terraform fmt/validate and plan with no write privilege; separate protected, approved deploy workflow uses short-lived federated identity and environment gates. Record plan output as an artifact with sensitive values redacted. Rollout dev → staging → prod only after access review, lineage, rollback and incident runbook.

Interview discussion prompts: Who owns definitions of revenue and stock? What freshness and completeness SLOs matter? How do schema changes and late events trigger reconciliation? What spend/permission boundaries separate experimentation from production?
